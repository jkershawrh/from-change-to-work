# Repeatable capability-transfer action

The existing Rust lifecycle now has a verified EVY network entry point. In the isolated Flightpath proof, the existing EVY FastAPI gateway dispatched approved capabilities to the same Rust action/executor on a different Intel/RHEL OpenShift worker. Inspection and rework used one six-axis simulator profile. They do not establish inspection-quality release or a complete rework process.

The existing EVY gateway is reused through the private patch in `verification/evy-action-integration-02/evy-capability-action.patch`; the exact deployed backend is retained in the successful proof’s source snapshot. EVY’s original public repository and serving deployments were not changed. Its corpus-specific governed distribution was not repurposed into a robotics controller.

An authenticated operator submits `evy.capability-action.v1` at `POST /actions/capability-transfer`, selecting the action ID, enrolled edge ID, capability ID and exact release digest. `GET /actions/catalog` lists configured profiles, and `GET /actions/capability-transfer/{action_id}` observes the edge. Viewer credentials cannot submit. Requests cannot supply URLs, config paths, commands, trust roots or physical-motion authority.

EVY durably binds the action and destination. A bounded HTTPS reference inbox accepts it durably before acknowledgement; Rust then receives and verifies approved signed bytes, activates while idle, executes a pinned release and retains a receipt. A duplicate terminal request returns the retained result without reexecution. Loss of central connectivity does not enter the local control loop. Executor death requires explicit local recovery and a new deliberate action ID. The reference HTTP inbox is Python; verification, lifecycle state and simulated execution remain Rust.

Reuse this process per use case by providing a signed capability, a compatible preinstalled executor profile, locally approved release identity and task acceptance criteria. For a new embodiment, implement and review the local adapter and compatibility/resource rules, then repeat the common TDD/EDD/CDD/BDD/CBT rejection, crash, disconnection, recovery and execution audit gates. A contract does not make an untested robot compatible. The current profile transfers bounded deterministic goal recipes, not arbitrary model weights or executable plugins.

See `verification/evy-action-integration-03/result.json` for the scoped green simulator gates, amber trust/production readiness and red physical/hard-real-time gates. The frontend workbench at `/?actions=1` now calls the actual EVY action path through the same-origin console. It exposes simulator-only transfer, data-plane disconnect/reconnect, interruption and explicit recovery. The authored-fixture `UseCase` catalog stays a separate contract; it is linked to this action workbench without claiming its fixture receipts are real execution. The standalone private handoff is `jkershawrh/evy-aeris-edge-actions`. Dynamic plugin loading and physical actuation remain disabled.
